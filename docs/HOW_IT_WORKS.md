# 实现原理与逆向过程

这份记录对应一台 EOS R7 和固定版本 Mac 软件。结论分为已观察事实、实现方法和仍未解决的部分。

## 观察到的载体

Picture Style Editor 导出的真实 PF3 示例为 434490 字节。不同内容和版本不应假设长度相同。通过本机 `EdsCFParse` 读取属性，发现两个各 215628 字节的 33³、3 通道、12-bit 色表（属性 `0x40001070`、`0x40001071`；每个节点 3 个 little-endian 16-bit 值）。名称在 `0x40001002`。基础模板的两张表不完全相同，因而分别合成。

如果只将 CUBE 写进 PF3，再用 PSE 打开并另存，PSE 会把本次修改的两张表重建为中性基础表。它能打开文件不等于效果进入机身。这是实验中发现的第一个分界点。

实际 R7 注册传输的是 83076 字节原生载荷 `0x01000203`，对应用户定义槽位参数 33、34、35。指定版本的原生编译器得到四段各 19652 字节的 17³ 色表，及位于偏移 78980 的 4096 字节实时预览辅助表。段位置和原始载体通过逐字节匹配确认，再进行替换，不从零拼出整份载荷。其余字节保留原生编译器输出。

## 转换代码做的事

1. `core.js` 解析纯 3D CUBE。读取 `LUT_3D_SIZE`、可选 DOMAIN；按 R 为最快变化轴三线性插值，重采样到 33³，限制到 12-bit 范围。
2. `src/cfp_bridge.py` 用本机合法安装的解析器读取真实 PSE 模板，把 LUT **分别**合成到两张 33³ 色表，只改名称和这两张表，重新读取验证属性往返一致。不会连接相机。
3. `src/compile_r7_dense.py` 验证解析器 SHA-256，给其传入从**本机 R7**读取的模型 ID 与机型描述符。它在自己的进程内构造 profile 对象，复制虚表到自己内存，令原生 17³ 生成路径处理更新后的两张表；再从原生接口生成预览辅助表。它不会给 EOS Utility 注入代码，也不连接相机。
4. `src/eds_install_one.m` 使用用户本机 EOS Utility 附带的 EDSDK。先检查机型和完整快照，再只写目标槽位；读回整个载荷并核对控制值与参数。它不刷相机固件。

EDSDK 版本钉死为 SHA-256 `35a425fc84460bac539eb051b921362c142dfcde966514b18249be8c393529ea`；解析器版本钉死为 SHA-256 `f4f2f931c174bfb200fde98d26c0e35c6bcaa3cf2374dbf89583bbeb7fe866b5`。其中内部 C++ 符号和对象布局不是稳定公开 API。出现版本差异就停止；改版本需要重新观察 ABI、偏移和行为。

## 为什么还要走一次官方注册

先用 EOS Utility 官方流程把有效 PSE 基础文件注册到目标用户槽位，会建立与该槽位对应的控制值（本次为 65、66、67）和一组有效参数。单纯设置 `0x01000203` 的内容不会补齐这一步。实验代码只替换原生载荷，保留官方已建立的控制值与参数；写后验证它们未改变。

佳能[官方手册](https://cam.start.canon/ky/S003/manual/html/UG-02_CameraSetting_0020.html)说明 PSE 文件可注册到用户定义 1–3，并在 R7 适用机型列表内。官方流程本身不支持将任意 `.cube` 直接注册为照片风格；这里的原生载荷替换为研究步骤。

## 两次重要修正

最初用零填充构造 PF3，机身曾出现 Err 10 和黑屏。我们撤下测试文件、切回内置标准，用户确认相机恢复正常；之后改为要求真实 PSE 基础文件，并拒绝零填充关键属性。不能断言最初错误只由这一原因造成。

第一次只替换四段 17³ 色表时，JPEG 的红蓝交换生效，实时取景仍显示原色。补齐原生生成的 4096 字节辅助色表后，电脑端取景和用户观察到的机身预览也发生了交换。这证明预览不能只靠 JPEG 色表判断。

## 适用范围

R7 上验证过照片风格的预览、JPEG、读回和一次富士 NC 的断线重启确认。普通 RAW 在第三方软件中的色彩行为与 JPEG 不同。结果并不证明任意 Log LUT、任意软件版本、R5 或其他机型都可直接套用。颜色是否与源 LUT 一致必须看输入色彩空间和实拍对照。
